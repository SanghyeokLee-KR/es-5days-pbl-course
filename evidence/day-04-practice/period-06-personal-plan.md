## (개인·필수) 문제 1 — 사용자와 판단 하나로 좁히기

### 답안

- 내 주제: 쇼핑몰 백엔드 log4j 로그 트러블슈팅 검색 시스템
- 한 문서의 의미: log4j2 JSON Layout으로 남은 로그 이벤트 1건
- 사용자 한 명: 백엔드 온콜(장애 대응) 담당자
- 사용자가 반복해서 하는 일: 알림을 받으면 최근 로그를 열어 어떤 예외·상태코드가 늘었는지 확인
- Dashboard를 보고 결정할 것: 어떤 예외 유형을 우선 조치할지
- 결정 뒤 수행할 행동: 우선순위가 높은 예외를 일으키는 서비스·코드를 이슈로 등록
- 사용자에게 필요 없는 정보: 개별 요청의 `trace_id` 원문 목록(집계 화면에서는 불필요, 상세 조회는 Discover에서 별도로 함)

## (개인·필수) 문제 2 — 서로 중복되지 않는 질문 4개

| 번호 | 분석 질문 | 질문의 답으로 내릴 판단 | 다른 질문과 겹치지 않는 이유 |
|---|---|---|---|
| Q1 | 전체 로그가 몇 건인가 | 전체 규모 파악, 이후 비율 계산의 기준 | 단일 숫자, 그룹·분포를 다루지 않음 |
| Q2 | 로그 레벨(INFO/WARN/ERROR) 비율은 어떤가 | 심각도 구성이 정상 범위(70/20/10)인지 판단 | Q1과 달리 레벨별 그룹 비교 |
| Q3 | 로그 레벨별로 어떤 예외 클래스가 주로 발생하는가 | 우선 조치할 예외 유형 판단 | Q2(레벨만)와 달리 예외 클래스까지 한 단계 더 나눔 |
| Q4 | HTTP 상태 코드는 어떻게 분포하는가 | 5xx(서버 오류) 비중이 큰지 판단 | 로그 레벨이 아니라 응답 코드라는 별도 축 |

## (개인·필수) 문제 3 — 질문별 field 존재 여부 점검

| 질문 | 필요한 field | mapping type | 실제 존재 | 값이 충분히 분포 | 가능/가공 필요/추가 필요 |
|---|---|---|---|---|---|
| Q1 | (전체 문서) | - | 있음 | - | 가능 |
| Q2 | `log_level` | keyword | 있음 | INFO 711 / WARN 188 / ERROR 101 | 가능 |
| Q3 | `log_level`, `exception_class` | keyword, keyword | 있음 | 레벨×예외 조합 다양 | 가능 |
| Q4 | `http_status` | integer | 있음 | 200/500/504/404 4종 | 가능 |

- 현재 데이터로 바로 만들 수 있는 질문 수: 4 / 4
- 선택한 A/B/C 경로: A(개인 데이터로 제작)
- 선택 이유: `shop-logs`에 질문 4개에 필요한 field가 모두 이미 있어 별도 보강 없이 개인 데이터로 제작했다.

## (개인·필수) 문제 4 — 부족한 데이터 생성 규칙 설계

질문 4개 자체는 현재 데이터로 모두 답할 수 있었다. 대신 "답하고는 싶었지만 필드가 있어도 Dashboard 설계(Control 미생성)로 인해 실제로는 답하지 못한" 질문을 기록한다.

- 답할 수 없는 질문: 서비스(`service_name`)별로 예외·상태코드가 어떻게 다른가
- 부족한 field: 없음 — `service_name`은 이미 존재한다.
- mapping type: keyword
- 예시값 3개: `order-api`, `payment-api`, `user-api`
- 범주라면 고유값 수: 4개(Day2 evidence 기준)
- 수치라면 최소·최대·대표 구간: 해당 없음
- 상태라면 예상 비율: 해당 없음
- 날짜라면 기간과 단위: 해당 없음
- 다른 field와 필요한 관계: `log_level`, `exception_class`, `http_status`와 함께 breakdown 되어야 서비스별 차이를 볼 수 있음
- 한 문서를 생성하는 규칙: 해당 없음(이미 존재하는 데이터)
- 필요한 문서 수와 이유: 해당 없음
- seed 고정 여부: 해당 없음(신규 생성 아님)
- 생성 후 검증 방법: 해당 없음

field는 있지만 Dashboard에 `service_name` 기준 Control/Filter를 만들지 않기로 결정해서 화면에서 바로 나눠 볼 수 없는 상태다. 이는 데이터 부족이 아니라 설계 범위를 좁힌 것이다(`evidence/day-04/dashboard-review.md` 참고).
